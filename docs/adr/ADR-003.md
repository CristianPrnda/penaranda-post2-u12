# ADR-003: Spring Events (Observer) para notificaciones desacopladas

## Estado: Aceptado — 2026-05-20

## Contexto

El servicio de pedidos necesita notificar a multiples receptores (email, log, y
potencialmente SMS u otros canales futuros) cuando un pedido es procesado exitosamente.
El acoplamiento directo a `JavaMailSender` en el servicio legacy hace fragil el servicio
central: agregar un nuevo canal requiere modificar `FachadaPedidos` y aumenta su CC.

## Decision

Se usa `ApplicationEventPublisher` de Spring (implementacion del patron Observer) para
publicar `PedidoProcesadoEvent` cuando un pedido es procesado. Cada canal de notificacion
implementa un `@EventListener` independiente (`NotificacionEmail`, `NotificacionLog`).
`FachadaPedidos` solo conoce el publisher, no los listeners concretos.

## Consecuencias

**Positivas:**
- Agregar un nuevo canal de notificacion (ej. SMS) no requiere modificar `FachadaPedidos`.
- Los listeners son opcionales: si no hay suscriptores, el evento se ignora sin error.
- Cada listener es testeable de forma independiente.

**Negativas:**
- El orden de ejecucion de listeners no esta garantizado por Spring Events.
- El debugging es mas complejo: hay que rastrear todos los `@EventListener` del
  contexto para entender que ocurre tras publicar el evento.
- Si un listener lanza excepcion, puede afectar la transaccion del publicador
  si no se configura `@Async` o manejo de errores explicito.
